========================
1. PROJECT IDENTITY
========================

Project name: BikeWatch

One-line pitch:
BikeWatch is a real-time bike theft awareness and prevention platform that helps people avoid high-risk parking and routing decisions using live incident mapping, hotspot visualization, and an AI assistant for safer biking choices.

Short elevator pitch:
Bike theft is common, frustrating, and often preventable, but theft data is fragmented, delayed, and not actionable in the moment. BikeWatch turns scattered theft incidents into a live, visual intelligence layer that helps riders identify hotspots, report suspicious activity, and make safer parking and routing decisions. The MVP combines interactive geospatial mapping with a lightweight AI copilot experience.

Core theme:
Prevent theft before it happens by turning fragmented incident reports into actionable, real-time guidance.

Primary value proposition:
BikeWatch does not just show theft after the fact — it helps users actively avoid risk.

3. PRODUCT VISION
========================

Who it is for:
- urban cyclists
- students commuting by bike
- scooter / e-bike riders
- campus communities
- city residents
- neighborhoods and local communities who want visibility into theft patterns

Problem:
Bike theft is rising and prevention is weak because people lack an easy way to understand where theft is happening, where risk is clustering, and what actions they should take.

User jobs to be done:
- “I want to know if this area is risky before I lock my bike.”
- “I want to avoid unsafe routes or parking areas.”
- “I want to see theft hotspots near me.”
- “I want to report a theft or suspicious activity quickly.”
- “I want guidance, not just raw data.”

Core promise:
BikeWatch helps riders make safer decisions using live map intelligence and AI-assisted recommendations.

========================
4. MVP SCOPE — WHAT MUST EXIST
========================

The MVP should include ONLY the highest-leverage features necessary for a compelling demo.

MVP Feature 1 — Interactive Risk Map
- A city map centered on one chosen demo city
- Preloaded theft incidents shown as pins or markers
- Markers should render instantly
- Clean, polished visual style
- Filters optional but not required

MVP Feature 2 — Hotspot / Risk Visualization
- Heatmap or danger zones indicating theft concentration
- Clear visual distinction between low-risk and high-risk areas
- Red / orange / yellow risk language is acceptable
- This must look visually impressive and easy to understand

MVP Feature 3 — Incident Reporting Flow
- User can report a new theft or suspicious event
- On submit, a new pin appears on the map
- Optional: hotspot intensity updates visually
- This can be mocked/static on the backend as long as it works in the demo

MVP Feature 4 — AI Copilot Interaction
- A user can ask a high-value safety question such as:
  - “Where is it safer to park nearby?”
  - “What areas should I avoid?”
  - “What’s the safest route home?”
- The copilot responds with actionable, location-aware safety guidance
- The AI experience may be rule-based, hardcoded, mocked, or LLM-backed, but it must appear intentional and useful

MVP Feature 5 — Safe Route / Safer Zone Recommendation
- The app should visually recommend either:
  - a safer route that avoids hotspots
  OR
  - a safer nearby parking area / safer zone
- This can be implemented with a hardcoded or simplified route line if needed
- The important part is visual clarity and usefulness, not routing perfection

8. ENGINEERING STRATEGY
========================

Optimize for speed, reliability, and demo confidence.

Preferred build philosophy:
- simplest architecture that creates the best demo
- high polish on a narrow scope
- fake or stub low-value complexity
- hardcode where appropriate
- seed realistic local data
- prioritize front-end polish and deterministic flows

Recommended stack (adjust if needed, but keep speed in mind):
- Frontend: Next.js or React + TypeScript
- Styling: Tailwind CSS
- Map: Mapbox GL JS or Azure Maps (whichever is fastest / most reliable)
- State: lightweight local state or simple store
- Backend: optional minimal API routes only if needed
- Data: static seeded JSON or mock API
- AI: simple prompt layer, mocked AI logic, or real LLM call if easy
- Hosting: Vercel/Netlify/Azure Static Web Apps or fastest available option
Map and visual rendering are high-priority engineering concerns.
This is not just a functional GIS app — it is a demo-first product.

Engineering must prioritize:
- choosing a map style that looks premium and cinematic
- making the hotspot rendering smooth and visually impressive
- ensuring the heatmap is high contrast and readable on a projector / screen share
- minimizing visual clutter while maximizing visual impact
- tuning map zoom, colors, glow, opacity, and marker styling for presentation quality

If tradeoffs are needed, choose stronger visual presentation over lower-value backend complexity.

10. AI / COPILOT BEHAVIOR
========================

The AI feature must feel useful and productized.

The assistant should:
- answer in concise, practical language
- reference hotspot risk or safe areas
- give action-oriented output
- sound confident but not overly verbose
- be framed as safety guidance, not generic chat

Acceptable MVP implementation approaches:
Option A — mock / deterministic logic
- If user asks for safer parking, return a nearby safer zone
- If user asks for a safe route, show a precomputed safer route
- If near hotspot, warn user to avoid that area

Option B — LLM-backed response
- Use a small structured prompt with current map context
- Keep output short and operational
- Prefer deterministic UI wiring even if an LLM is involved

The AI should not feel like a general chatbot.
It should feel like a mobility safety copilot.

The AI recommendation output should also be visually reinforced on the map.
Whenever possible, Copilot responses should trigger visible changes such as:
- highlighted safer zones
- emphasized avoided danger areas
- a visually distinct safe route
- callout cards with clear risk reasoning

The AI should not only answer — it should make the map feel smarter.
